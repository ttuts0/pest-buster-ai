# Storage layer

How PestBusterAI stores drone images and their metadata.

## S3

- **Bucket:** `pestbusterai-images`
- **Region:** US East (Ohio), `us-east-2`

Key format:

```
raw/{vineyard_id}/{YYYY-MM-DD}/{flight_id}/{filename}.JPG
processed/{vineyard_id}/{YYYY-MM-DD}/{flight_id}/{filename}.jpg
```

Example: `raw/1/2026-11-16/3f2b8c1e-9a4d-4e6f-8b7a-1c2d3e4f5a6b/DJI_0042.JPG`

- `raw/` holds the original photos from the drone. Nothing else writes here.
- `processed/` holds the pre-processed (cleaned) images. The key is the raw key with the prefix swapped, so no column stores it.
- `vineyard_id` is `vineyards.vineyard_id`. `flight_id` is the flight's UUID, generated by the Android app. The flight folder keeps keys unique, because DJI filenames repeat.
- The date is the flight date.

## PostgreSQL

- **Instance:** Amazon RDS for PostgreSQL, `pestbusterai-db`, in `us-east-2`
- **Database:** `pestbuster`
- **Schema:** [`db/schema.sql`](../db/schema.sql)

| Table | Holds | Written by |
|---|---|---|
| `users` | Accounts | API server |
| `vineyards` | Vineyards | API server |
| `vineyard_members` | Which users belong to which vineyard, and their role | API server |
| `blocks` | Sections of a vineyard | API server |
| `flights` | One row per drone flight | Upload |
| `images` | One row per raw image | Upload |
| `disease_types` | Lookup list of diseases | Set up once |
| `detections` | One row per disease found in an image | Detection |

Records chain together as vineyard → block → flight → image → detection.

### `images`

| Column | Meaning |
|---|---|
| `flight_id` | The flight this image belongs to. The flight row must exist first. |
| `s3_key` | Where the original image is. Unique. |
| `sha256` | Hash of the file. Unique, so a resent batch cannot insert the same photo twice. |
| `original_filename` | The name the drone gave the file. |
| `captured_at` | When the photo was taken. Required. |
| `latitude`, `longitude` | GPS position in decimal degrees. Required. |
| `altitude_m` | Altitude in meters. |
| `analysis_status` | Where the image is in the pipeline (see below). |
| `uploaded_at`, `analyzed_at` | When the row was created and when detection finished. |

## Status values

`images.analysis_status`:

| Value | Meaning | Set by |
|---|---|---|
| `queued` | Row created, waiting for detection | Upload |
| `done` | Detection finished; any findings are in `detections` | Detection |
| `error` | Detection failed for this image | Detection |

`flights.status`:

| Value | Meaning |
|---|---|
| `uploaded` | Batch received, detection not started |
| `processing` | Detection is running on the flight's images |
| `complete` | Every image in the flight has been analyzed |
| `failed` | The flight could not be processed |

## Delete rules

- Deleting a flight deletes its images and their detections.
- Deleting a user keeps their flights, with the operator left empty.
- A disease type cannot be deleted while detections refer to it.
